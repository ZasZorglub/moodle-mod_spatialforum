# 0.9.0-dev whole-activity grading

Baseline: `bcec239480e5d7b70eda10d43f59e7275ba864f6` / `0.8.1-dev`. Implements S3: the user's confirmed choice of one teacher-assigned grade and feedback per participant, using Moodle Gradebook. Import and dedicated Moodle App support remain later slices.

## Contract and ownership

- New/upgraded activities default to `grade = 0` (None). Points up to 10,000 or a course/site scale with at least two items are configured through Moodle's standard grade form. The signed `number(15,5)` configuration field accommodates large negative scale IDs as well as decimal point maxima. No new grade/feedback table exists.
- Gradebook is authoritative for raw/final grades, feedback, visibility, protection, grader and audit history. Standard Grade API callbacks create/rename/delete items and report scale usage. Maintenance callbacks never re-derive manual grades from posts/reactions or clear missing local results. Changing type/maximum is blocked when scores or feedback exist.
- Grading requires authenticated activity access, `mod/spatialforum:grade`, an active target enrolment with `mod/spatialforum:receivegrade`, and current group authority. Normally teachers grade and students receive grades. In both visible and separate groups, the plugin requires a shared group inside the activity grouping unless the grader has access-all-groups. Forced course group mode applies. Ungrouped participants require an all-groups grader when grouping applies. The SQL roster counts/names and direct assessment/save APIs use the same boundary; roster pages contain at most 50 participants.
- Learner reads accept no arbitrary target ID. Web requests for another participant are denied. Only the current enrolled eligible user receives their own result; item/per-user hidden flags and disabled course-grade visibility withhold both grade and feedback. Gradebook itself applies Moodle's separate course-level permissions; this plugin does not revoke access granted independently by `moodle/grade:viewall` or other core capabilities. During QA, core Gradebook showed both visible-group participant names to the appropriately privileged teacher, while the plugin's assessment roster/direct URLs remained restricted to the teacher's shared group.
- Nullable grades distinguish never graded/cleared from zero. Plain-text feedback supports at most 10,000 characters and is escaped on display. Scale values are one-based integers. The form and save API validate ranges; blank scores can retain feedback. No public conversation renderer receives private assessment values.
- Saving rechecks authorisation and Gradebook state, uses a participant/activity Moodle lock, validates a revision fingerprint, and writes through `grade_update` in a transaction. Stale forms cannot silently overwrite a newer result. Item/user locks, scheduled lock cutoffs and overrides are protected. Calculations, adjustments, deducted marks and external rich feedback are read-only here. Manage those cases in Gradebook. Core Gradebook history and `user_graded` events provide audit evidence. Cross-system simultaneous writes are not an exactly-once guarantee; core Gradebook protection and the plugin's own serialisation remain distinct.
- Core activity-grade backup/restore owns user grades. Plugin backup adds configuration and scale annotation/remapping. Tests cover restored raw/final values, feedback, hidden state, locks, overrides and scale choices. Excluding users preserves configuration without participant results. Activity deletion calls the Grade API. Metadata links `core_grades`; its privacy provider owns discovery, export and erasure of grade/history data. Plugin post erasure does not directly rewrite core Gradebook tables.

## Release limits

Alpha development build, not an existing-test-server or Marketplace deployment. No automated participation scoring, per-post rating, rubric, feedback-file editor, bulk grading or plugin-specific grade-email template is introduced. Core Moodle messaging remains governed by its own settings. Screen-reader/physical-device checks, simultaneous independent Gradebook/plugin edits under load and large-course throughput remain open. Tests use synthetic data and do not prove production assessment policy or a customer's operational/privacy configuration.

Before deployment, back up database, Moodle data and plugin source; rehearse the upgrade, representative grade/scale backup/restore and permission policy. Preserve the previous package and a consistent database snapshot. Replacing old PHP alone does not reverse the Moodle version/schema change. Standard Gradebook history is available for grade review; a database backup is the rollback boundary for the release.
