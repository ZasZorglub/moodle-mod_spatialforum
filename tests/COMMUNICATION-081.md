# 0.8.1-dev administrator communication setup

Baseline: `00f4cc9356ac7310c42584a91446db9848ccd600` / `0.8.0-dev`. The user requested administrator control of which forum messages are sent, when, and their content. This slice adds site-wide communication controls to the existing opt-in queue. It does not implement the separately planned grading, forum importer or dedicated App client.

## Contract

- Only users with system `moodle/site:config` may save configuration or send a synthetic self-test. The web page additionally uses Moodle administration authentication, Moodleform validation and POST/session keys. Preview/test do not persist values. Saving does not send messages. The self-test API has no recipient/email argument.
- Enable root posts and replies independently, and enable individual messages/daily digests independently. A participant's own subscription and Moodle channel preferences remain authoritative. Disabled modes are labelled as paused. No forced subscription or unsolicited bulk campaign is introduced.
- Individual-message delay is 0–1440 minutes after publication. Daily digests use a selected hour/minute in recipient or site timezone. Cron runs at or after the deadline, not at a guaranteed exact time. Existing `digesthour` installations keep that hour until the new policy is saved; fresh defaults preserve the previous 17:00 recipient-timezone behaviour.
- Templates are plain text with a per-field variable whitelist. Unknown/incomplete substitutions, empty/oversized templates, invalid settings and multiline subjects are rejected. Templates allow at most 100 substitutions, with `{{posts}}` at most once in the digest body to prevent multiplicative expansion. Rendered digest items are limited to 4,000 characters and the body to 500,000 before essential links are appended. Interpolation is one-pass, rendered HTML is escaped, subjects remove interpolated tags/newlines, and authenticated post/preference links remain present even if omitted from the custom text. Saved custom wording is site-wide across languages. No arbitrary HTML, template execution, arbitrary recipients or attachments are accepted.
- Site configuration is stored atomically as plugin config and recorded in Moodle's configuration log. Timing/type changes queue an idempotent reconciliation task, limited to 250 pending rows per page. The same participant/activity lock serialises reconciliation with subscription changes and dispatch. New policy is read for every page. Pending retries keep at least their existing backoff; accepted/failed/uncertain rows are untouched. Dispatch also blocks disabled types and recalculates postponed deadlines. An earlier deadline is picked up after background reconciliation. Re-enabling does not recreate cancelled rows. Mail already accepted or in flight cannot be recalled.
- Configuration is site-level, not activity content, so activity backup/restore does not copy it. Existing queue/privacy/retention rules remain in force. Version `2026102902` is a configuration/provider-registration upgrade without new tables.

## Limits and release

This is an alpha development build. No existing-test-server or Marketplace deployment is implied. No real participant or external inbox receives test mail. Positive SMTP capture does not prove customer-provider deliverability. Browser testing is desktop English only; screen readers, physical devices, concurrent administrator saves and large live-course throughput remain unverified. Long-running daily operation is not established by advancing a synthetic test clock.

Apply the standard database/data/code backup before deployment. Rehearse the upgrade, cron reconciliation and site mail preferences with synthetic accounts first. Retain the previous build and a consistent database snapshot; reverting PHP alone is not a complete Moodle version rollback. Use the communication switches to stop future eligible dispatch while investigating; already accepted messages cannot be recalled.
